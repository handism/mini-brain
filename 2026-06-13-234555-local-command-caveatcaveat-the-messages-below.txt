⏺ 主要モジュール（AgentPipeline / SearchPipeline / RagPipeline / Reranker /
  CoverageChecker / Repository / Chunker / MetaExtractor）を読みました。明確にリ
  ファクタできるポイントが何個か見つかりました。短く優先度順に列挙します。

  高優先度（重複ロジック・脆い結合）

  1. DATE_QUERY_REGEX の三重定義

  同じ正規表現が 3 ファイルにコピペされています。1
  箇所が更新されると他がズレる。

  - AgentPipeline.kt:31 — companion object 定数
  - CoverageChecker.kt:19 — companion object 定数
  - LlmReranker.kt:55-56 — 関数内で毎回 Regex(...) インスタンス化
  されているのでホットパスでも重い

  → ai/agent/DateResolver.kt（既にある）に DateResolver.isDateQuery(query: 
  String): Boolean か DATE_QUERY_REGEX 定数として一本化。

  2. [日付: YYYY-MM-DD] プレフィックスのスキーマが各所に散らばっている

  プレフィックスの構築・パース・短絡判定がそれぞれ独立しています。

  - 構築: SearchPipeline.buildSnippetWithDate (SearchPipeline.kt:231)
  - パース: LlmReranker.DATE_PREFIX_REGEX (LlmReranker.kt:14)
  - 短絡: CoverageChecker.DATE_PREFIX = "[日付:" + startsWith
  (CoverageChecker.kt:18,24)

  → Citation 周りに DatePrefix ユーティリティ（build(date, body) /
  parse(snippet): Pair<String?, String>）を 1
  つ作って全部経由させる。スニペットフォーマットを変えるときの影響が 1
  ファイルに収まります。

  3. "${c.docId}::${c.headingPath}" のキー生成が散在

  RRF 融合、dateRange pin、multiVectorSearch dedupe、CitationIntegrator
  あたりでコピペで生成しています。

  - SearchPipeline.kt:146,147,276,383

  → Citation.dedupeKey: String extension property を生やして全部それ経由に。

  4. DocumentRepository.extractDateFromPath が二重定義

  - Companion.extractDateFromPath (line 49)
  - private fun extractDateFromPath(...) (line 265) — 単に Companion
  を呼び直すだけ

  → インスタンスメソッドを削除して呼び出し側を Companion.extractDateFromPath
  直接呼びに統一。

  中優先度（構造）

  5. AgentTool の sealed-class ハンドリングが 4 つに分裂

  AgentPipeline.kt:251-289 で traceToolName / traceToolArgs /
  traceObservationSummary / toolProgressDescription が同じ when を 4
  回繰り返している。ツール追加時に 4 箇所変更が必要。

  → AgentTool 自身に displayName / traceArgs() / progressLabel
  を持たせるか、AgentToolDescriptor 1 つに集約。RRF 系の when
  と違ってここは普通に拡張に弱い設計。

  6. RRF ロジックが 2 種類実装されている

  - mergeCandidatesRrf (SearchPipeline.kt:369 — Citation ベース、weights 対応)
  - RagPipeline.rrf (line 225 — ChunkEntity ベース、weights 無し、freshness
  boost 込み)

  ロジック本体（Σ 1/(k+rank+1) で集約してソート）は同一です。weights と
  post-processing（freshness）だけ差し替えれば 1 つに統合可能。

  7. historyBlock の組み立てが AgentPipeline 内で 2 回重複

  buildDirectAnswerPrompt / buildAnswerPrompt で同じ takeLast(6).joinToString
  を書いている (AgentPipeline.kt:295-299, 381-385)。

  → private fun に括る。RagPipeline.buildPrompt (line 291)
  にも同型コードがあるので、PromptUtils 的なファイルにまとめても良い。

  8. RagPipeline.buildPrompt が dead code 疑い

  RagPipeline.answer() (line 114)
  は呼び出し元があるか怪しい。AgentPipeline.buildAnswerPrompt
  がプロンプト生成を全部担っており、answer/buildPrompt
  は同じことを別フォーマットでやっている重複。

  → 使われていないなら削除、使われているなら AgentPipeline のものに寄せて 1
  本化。

  低優先度（小ぶり）

  9. estimateTokens を util へ

  AgentPipeline.kt:404-409
  の日本語/英語混在トークン推定は他箇所（CitationIntegrator?
  Reranker?）でも欲しくなる典型。util/TokenEstimator.kt に出すと再利用しやすい。

  10. MarkdownMetaExtractor.extractDateFromContent 
  内の重複した「年範囲＋LocalDate validity」チェック

  safeDate / safeMonth はクロージャ化されていて読みやすいですが、DocumentReposit
  ory.extractDateFromPath も完全に同じ「1990..今年 / LocalDate.of
  validity」検査をしています (DocumentRepository.kt:50, 64, 76)。→
  DateValidator.parseSafe(y, m, d?) を 1 つ作って両者で共有。
